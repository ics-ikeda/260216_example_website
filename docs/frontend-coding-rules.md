# Frontend Coding Rules

## 目的

- 本ドキュメントは、プロジェクト全体で適用する実装規約を定義する。
- 迷った場合は、正しさ・一貫性・単純性・検証容易性を優先する。
- ルールは例示ではなく必須要件として扱う。

## 適用範囲

- HTML
- CSS
- TypeScript / JavaScript
- 画像 / SVG / アイコン
- ビルド前検証

## 基本原則

- 同種問題は同種解決で揃える。
- 局所最適より全体一貫性を優先する。
- 過剰実装を避ける。
- 不要コードを残さない。
- 一時対応を恒久実装にしない。
- 例外は最小限にする。
- 例外を入れる場合は理由を明示できる状態にする。

## HTML

- 同一ソースしか使わない `picture` は使わず `img` を使う。
- `picture` はアートディレクションが必要な場合のみ使う。
- 役割のない装飾画像は原則CSSで表現する。
- 非装飾画像は適切な `alt` を付ける。
- 装飾画像は空 `alt` を使う。
- 意味のないラッパー要素を増やさない。
- 既存のセマンティクスを壊さない。
- クリック可能要素は `button` / `a` を用途で使い分ける。
- トグルUIをフォームハックで実装しない。
- `input[type=checkbox]` でメニューやモーダル制御をしない。
- モーダルは `dialog` + `command` / `commandfor` を基本とする。
- 未使用の属性・クラス・要素を残さない。

## 画像とアセット

- 写真画像の形式は原則 `avif` を使う。
- 写真画像に `png` は使わない。
- 透過UI素材や図版など非写真用途では `png` を許可する。
- 画像解像度は実表示サイズのRetina 2xを上限とする。
- 過大解像度の画像を公開物として残さない。
- 画像変換後は見た目確認を必ず行う。
- 変換後に白抜け・透明化・色化けがないことを確認する。
- 不要になった元画像は削除する。
- アイコンSVGに `style` 属性を直接書かない。
- SVGは属性または外部CSSで制御する。
- アセット命名は用途が分かる名前にする。

## CSS 基本

- 要件にない過剰な対応はしない。
  - `@media (prefers-reduced-motion: reduce)` は使わない。
  - `:focus-visible` は明示要件がない限り使わない。
- 過剰でレガシーな最適化手法を使わない。
  - `will-change` は使わない。
  - 3D変換が不要な場合は `translate3d` を使わない。
- `vh` と `dvh` を同一箇所で併記しない。
- 旧世代ベンダープレフィックスを使わない。
- 継承や既定値で足りる指定は追加しない。
- 数値 `font-weight` は使わない。
- `font-weight` は `normal` / `bold` を使う。継承で成立する場合は `inherit` を使う（未指定とする）。
- `line-height` を固定値で乱用しない。
- `margin: 0` / `padding: 0` は必要箇所だけに書く。
- `background: transparent` / `border: none` も必要箇所のみ書く。

## CSS 記法

- CSS Nestingを優先する。
- 分離セレクターより内包Nestingを優先する。
- 親状態依存の子要素指定は親ブロック内にまとめる。
- 疑似クラスの分散記述を避ける。
- `row-gap` と `column-gap` の併記を避ける。
- 間隔指定は `gap` に統一する。
- `display` は多キーワード構文を優先する。
  - 旧1値構文へ戻さない。
- 1箇所だけのための抽象変数を作らない。
- CSS変数は再利用される値だけに使う。
- 定義1回・利用1回のCSS変数はハードコードする。
- 変数導入で可読性が落ちるなら導入しない。

## メディアクエリ

- レンジ構文を使う。
- 境界条件は帯域全体で一貫させる。
- 範囲条件は連鎖レンジを優先する。
- `and` 連結は使わない。
- 一箇所変更時に周辺帯域も必ず確認する。
- PC / タブレット / モバイルの帯域意図を先に定義する。
- `<`や`<=`を適切に使い分ける。メディアクエリの境界値に対して、`-1`や`+1`をした値で`<=`や`>=`を使わないこと。

## モーション

- UIモーションは必須。
- モーション実装は可能な限りCSS主体にする。
- `@starting-style` と `allow-discrete` を優先する。
- `transition` は原則 `0.3s` を使う。
- 離散遷移が必要な場合のみ `0.3s allow-discrete` を使う。
- `transition` をプロパティ分割で細かく書かない。
- イージングは明示要件がない限りデフォルトを使う。
- ホバー時移動量は最小限にする。
- スタッガーは `sibling-index()` を優先する。
  - `nth-of-type` 依存のスタッガーは禁止。

## オーバーレイ / モーダル / メニュー

- 開閉中は背景スクロールを禁止する。
- オーバーレイ表示中は非対象UIの干渉を防ぐ。
- 閉じる操作が常に到達可能な位置にあることを保証する。
- ナビゲーションボタンは主要コンテンツを阻害しない配置にする。
- 主要コンテンツは視覚的中心を維持する。
- 開閉トランジションの開始・終了状態を明確にする。
- レイアウトシフトを起こさない。

## ファイル構成

- スタイルは役割単位で分割する。
- 状態が大きく異なるUIは別ファイルに分離する。
- ルートスタイルファイルは import ハブとして使う。
- 巨大ファイル化したら責務分解する。
- 命名は短くても意味が分かることを条件にする。
- 省略語で意味が失われる命名は避ける。

## TypeScript / JavaScript

- 過剰な後方互換防御コードを入れない。
- 不要な `instanceof` を入れない。
- 意味の薄いフォールバックを増やさない。
- 分岐は必要最小限にする。
- 命名は短く明確にする。
- JSDocは必要箇所で維持する。
- 型は原則必須プロパティで設計する。
- オプショナルは必要最低限に限定する。

## 検証手順

- 変更後は次を順に実行する。
- `npm run lint`
- `npm run fmt`
- `npm run build`
- レイアウト変更時は Playwright MCP で desktop / mobile を確認する。
- デザイン参照タスクは Figma と Playwright スクリーンショットを照合する。
- 画像形式変更時はデコード不具合を確認する。
- 実行不能な検証がある場合は未実施理由を記録する。

## コミット前の運用

- 差分に未使用アセットが含まれていないことを確認する。
- ルール違反を「後で直す」前提でコミットしない。
- 例外実装がある場合は理由をコミット説明で明示する。
- コミットメッセージは日本語で記述する。

## ルール更新方針

- 同内容を別セクションへ再掲しない。
- 既存ルールで表現できる場合は追記で済ませる。
- 新ルールは検証可能な文面で書く。
- 禁止事項だけでなく、代替手段も明示する。
- 一時的事情を恒久ルール化しない。

## Playwright確認項目

- 初期表示で主要セクションのレイアウト崩れがないことを確認する。
- desktop と mobile の両方で確認する。
- メニュー開閉時にスクロールロックが効くことを確認する。
- オーバーレイ表示中に背景操作が無効化されることを確認する。
- 閉じるボタンが常に視認可能か確認する。
- ナビゲーションボタンが画像を遮蔽しないことを確認する。
- 画像の表示位置が縦横中央基準で維持されることを確認する。
- 開閉や遷移時に不自然なチラつきがないことを確認する。

## Figma照合の運用

- 比較対象ノードを明確にしてから確認を開始する。
- 比較は余白・サイズ・線・タイポグラフィ・配置を確認する。
- 画面幅依存の差異は複数幅で確認する。
- 差異があれば、実装値とデザイン値をセットで記録する。
- 反映後は再度同ノードで再確認する。

## 画像最適化の運用

- 変換前に現在の実表示サイズを把握する。
- 変換後に実ファイル寸法が上限を超えていないことを確認する。
- 変換後に色味と階調が破綻していないことを確認する。
- 変換後に透過情報が不要に付与されていないことを確認する。
- 置換後は参照切れがないことを確認する。

## CSSレビュー観点

- 指定値が必要最小限かを確認する。
- 同じ意図を複数記法で書いていないか確認する。
- 命名が意味を保ったまま短くできるか確認する。
- ファイル責務が混在していないか確認する。
- 既存の命名規約から逸脱していないか確認する。
